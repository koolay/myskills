## 独立取舍

| 原方案思路 | 保留或调整 | 原因 |
| --- | --- | --- |
| 领域、系统、现实约束、AI 任务边界 | 保留，并增加阶段退出条件 | 把思维框架转成可执行决策 |
| 忠诚与长期架构承诺 | 改成契约保护及有证据的重新决策 | 兼容性有价值，过时或有害的选择需要退出机制 |
| 每次都问完整问题清单 | 先读上下文，仅询问影响决策的缺口 | 已知约束不应反复询问，小任务不应进入架构流程 |
| 每块任务后人工检查 | 已授权执行继续；重大判断和不可逆动作按权限处理 | 保留责任边界，减少无意义审批 |
| AI-first 工具目录与泛关键词触发 | 按实际需求评估 AI，限定架构决策触发 | 减少技术追潮和错误激活 |
| 固定规格层级、完美结构、默认 100% 覆盖率 | 复用现有文档和质量门槛，按风险规划验收 | 一致性和覆盖率不能证明业务正确，也不应抹掉项目明确要求 |
| 所有任务完成即可保证整体实现 | 增加真实边界集成检查、失败恢复与混合版本验证 | 局部成功会遗漏组合故障与发布窗口 |

新增的关键决策规则：支付超时可能是结果未知；写操作不能盲目重试；共享 schema 需要明确所有权；回滚代码未必恢复数据；未知责任人和指标必须显式标注。

## 手工行为验证

方法：对 [evals/evals.json](../evals/evals.json) 的六个场景进行同一作者的手工推演。RED 为未使用 skill 时的可能失败，不是实际基线运行；GREEN 为按照当前规则生成的简短决策结果。未运行独立 agent，也未执行应用、支付或迁移测试。这些记录支持规则可应用性，不证明真实 agent 的稳定遵循率。

### 1. 追潮重写

- RED 风险：把多 agent 和微服务当目标，扩大两周交付范围。
- GREEN 推演输出：在现有 Django/PostgreSQL 中交付导出，先确认导出字段、权限和数据量；这些是验收假设。现有系统运行正常，没有证据支持拆服务。大数据导出的处理方式待实际需求决定。只给方案，不写代码或启动 agent。
- 判断：满足阶段 1、3 和权限边界；未知导出规模没有被伪装成测量结果。

### 2. 支付响应丢失

- RED 风险：超时即失败，用新键重试导致重复扣款。
- GREEN 推演输出：为一次支付意图固定幂等键；超时进入待确认状态，通过按键查询和回调收敛到支付商结果。回调去重，并限制状态转换。计划验证支付商成功但响应丢失、重复回调和乱序回调，本地只产生一次业务效果。监控待确认订单的停留时间，阈值和处置责任人待确定，不宣称已验证。
- 判断：覆盖未知结果、重试边界、检测和组合验收；没有承诺消息恰好投递一次。

### 3. 有害承诺退出

- RED 风险：为了旧约定拒绝迁移，或直接切断旧客户端。
- GREEN 推演输出：执行用户要求的受支持版本迁移规划；公共 API 的兼容承诺继续有效。先证明新旧客户端在过渡期可用，再分阶段切换。若涉及数据格式变化，先使旧版本能够读取新写入数据，或明确只能向前修复；不能把回滚应用版本当成数据恢复。
- 判断：旧技术选择可修订，用户明确迁移要求不被最小改动原则否定。

### 4. 单测全绿与整体正确

- RED 风险：覆盖率和三个任务完成被当成订单正确性证明。
- GREEN 推演输出：结论证据不足。计划跨服务验证库存已预留、支付成功而响应丢失的流程；支付未知时不能直接以扣款失败为依据释放库存并重新扣款。核验重复消息不重复产生业务效果，待确认订单可对账收敛，库存预留按明确契约消费或释放。超时阈值和预留规则是待定领域契约，需要处理未知结果长时间不能收敛的情况。
- 判断：同时考虑安全性和最终进展，没有用臆造的业务规则补全规范。

### 5. 共享契约拆分

- RED 风险：两个 agent 同时修改共享 schema，或新生产者使旧消费者失效。
- GREEN 推演输出：先确定兼容契约和共享 schema 的唯一修改责任。若可做兼容的增量扩展，先升级消费者兼容读取，再切换生产者，最后清理旧字段；若无法兼容，评估事件版本并行。每个实现任务列出上下文、所有权、依赖和检查，验收使用真实生产者/消费者及混合版本。这里只提供计划。
- 判断：按实际兼容性选择顺序，未假定可随意并行，未启动 agent。

### 6. 触发与缺失信息

- RED 风险：按钮文案也走完整架构问卷；跨区域设计默认存在数据出境许可。
- GREEN 推演输出：A 是本地文案修改，走普通执行。B 询问已确认的数据驻留/出境约束；在答案到来前暂停部署区域和供应商选择，继续梳理同步的输入输出、冲突语义、失败检测与恢复，所有位置选择保持未定。不会联系外部人员。
- 判断：触发范围适当；阻塞只影响相关决定。

首次推演发现两个边界需要显式化：用户已经要求迁移时，保留现状只能作为成本比较；未知数据兼容性下不能保证回滚。初版已补充规则，场景 3、5 已按当时的修订规则重走。

结构检查：命名及已注册分类、frontmatter、必要章节、六个场景的 JSON 和新增相对链接均通过标准库检查，`git diff --check` 通过。官方 `quick_validate.py` 因环境缺少 PyYAML 未能运行，没有为此安装依赖。全量链接检查发现 `index.md` 中已有的 research 链接目标缺失；本次只验证新增或变更的链接，未修补无关文档。

## writing-great-skills 审查与优化

按用户指定的 writing-great-skills 及其 GLOSSARY 审查。以下是静态审查发现的执行风险，未声称来自独立 agent 的实际失败：

| 发现 | 修改 |
| --- | --- |
| 触发描述与正文 Use when 重复，多个词描述同一决策分支 | 保留自动发现，description 以 architecture decisions 为锚点，合并重复触发 |
| recommendation-only 请求也会走任务拆分 | Inputs 限定默认范围，步骤 4 设置明确进入条件 |
| 单一代表流程可能遗漏其他验收路径；完成条件没有穷尽检查 | 每种验收路径均追踪边界，每个契约、故障、验收项均有对应 disposition 或检查 |
| 权限、缺失证据和人工决策规则分散重复 | 将阻塞行为集中到 Halt Conditions，步骤引用该规则 |
| 非迁移决策也加载发布和数据回退细节 | 拆至 migrations.md，步骤 2 的指针由契约不兼容或持久化格式改变触发 |
| 通用原则和否定式指导占用正文 | 删除与步骤重复的段落，以可执行目标替换可正向表达的禁止句 |

没有为了缩短而拆成多个可调用 skill，也没有添加外部 skill 依赖。完成条件先在当前步骤内强化，未以未经验证的提前结束风险为由增加多 agent 或强制人工交接。

### 修订后手工回归

同一作者按修订正文重走原六个场景，并新增两个非电商场景；结果仍为手工推演，不是独立运行。

- 原场景 1、2、4、6：最小方案、支付未知结果、真实边界检查与决策缺口处理仍由步骤 1-3 和 Halt Conditions 覆盖。推荐型任务在完成建议和计划检查后结束。
- 原场景 3：按实际是否改变消费者契约或数据格式决定读取迁移参考；支持版本迁移是硬要求，旧选择不构成阻止迁移的理由。
- 原场景 5：事件不兼容升级触发迁移参考；先定义共享契约及所有权，再拆分依赖任务，明确集成责任和混合版本检查。
- 新场景 recommendation-only-tooling 的推演输出：先用已有服务标签满足服务名检索；计划用代表服务名核验相关手册检索结果。如果用户需要跨词义检索且现有方案无法满足，再评估向量库。省略任务拆分和迁移参考；没有虚构检索实测数据。
- 新场景 document-format-migration 的推演输出：读取迁移规则；核验两种客户端的读写兼容性。对于无法无损降级的新数据，需要确定兼容表示、限制过渡期写入或向前恢复策略，未知条件作为决策缺口。为一周共存窗口提出待确认的停止信号，计划真实客户端混合读写和恢复检查。拆分契约、数据转换、客户端和集成验收任务，共享格式与集成均指定责任角色；未执行迁移或声称通过验收。

检查边界：回归中的支付处理来自该场景提供的领域契约；正文保持跨领域规则。迁移参考只在指针条件成立时加载，八个场景的期望结果不作为运行时指令来源。

修订后结构检查通过：frontmatter、已注册分类、必要章节、四个完成条件、自动发现配置、八个场景 JSON 及新增相对链接。`git diff --check` 通过。正文从 1,287 减至 976 个空白分隔词，从 9,749 减至 7,420 UTF-8 字节，减少约 24%；这是文本量度，不是 tokenizer 测量。新增迁移参考为 1,643 字节，仅在指针触发时加载；维护记录的增长不计入日常运行正文。官方校验脚本的 PyYAML 缺失限制仍然存在。

## 架构设计输出规范

按用户要求增补 references/architecture-output.md。一手来源与采用范围列在该文件末尾：arc42 的内容覆盖、质量场景和决策记录，以及 C4 的视图选择和图表检查。此规范是项目裁剪约定，不宣称符合未评审的 ISO 标准。运行时仅在正式设计或较完整的评审方案中读取；轻量建议沿用 inline 输出。迁移的行为规则仍以 migrations.md 为唯一来源，输出规范只要求承载其结果。

### 手工场景复核

方法仍为同一作者手工推演；以下是规则应用结果，不是独立 agent 运行或应用测试。

| 场景 | RED 风险 | 应用规范后的推演输出 |
| --- | --- | --- |
| architecture-document-output | 只有技术框图，没有质量条件、权限语义或失败验收；把 30 秒目标写成实测 | 为研发标出契约和重复交付处理，为运维标出故障信号与恢复责任；用上下文、结构和导出/下载运行时视图说明边界。质量表记录 95%/30 秒为用户目标、负载条件未知、验证 planned。权限撤销到下载授权检查、重复交付到业务幂等、对象写失败到恢复各映射检查。成本和部署拓扑为影响可行性的缺口，方案保持 proposed，未生成代码。 |
| existing-template-and-provisional-quality | 强制新模板，或把已接受的方向当成细节全批准 | 将目标/约束放在背景，视图/契约/决策/风险和实施拆分放在方案，质量与验收映射放在验证。迁移方向 accepted，转换与部署方案 proposed，质量指标 unknown。加载迁移规则，列出不可逆新写入的恢复边界、共享格式所有权及混合客户端检查，注明实施就绪缺口。 |
| recommendation-only-tooling | 普通向量库建议也加载完整规范，产生无关文档 | 保持已有标签方案的简短建议、一个计划检索检查和重议条件；正式文档条件未满足，输出规范和迁移参考均不加载。 |

针对当前行为，十个场景包含正式文档、现有模板兼容以及不应加载完整规范的反例。手工复核支持指针与内容规则可应用性，真实调用稳定性仍需独立评测。
